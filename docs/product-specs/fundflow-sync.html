资金流数据中心化分发 — 产品稿

待确认sanhu · 2026-08-16
承接已上线的「资金流」功能（可行性分析 · 自动刷新与回放）。 目标：让每个用户不再各自去打东财，改为从统一的数据源同步。

一、结论先行

✅

方向完全对，但大概率不需要跑一台服务器 —— 静态文件就够了。

问题是真的：现在每个用户的 sanhu 都各自去打东财，日均约 13 次。 用户数上去之后，就是 N 个 IP 同时在刷同一份公开数据 —— 既容易触发限流（这个坑我们已经踩过）， 对东财也不礼貌。集中采集一次、大家来取，是正确的方向。

但「服务端」不一定意味着服务器。实测一个交易日的完整数据包 gzip 只有 79 KB，全年 19 MB。这个量级用静态文件 + CDN分发绰绰有余： 没有服务器要运维、没有月租、没有宕机风险，而且项目里已经有两个同类先例 —— seed.sql.gz（内嵌初始数据）和 SANHU_SEED_URL（允许从 URL 取种子）， 以及 updater 查 GitHub Releases。

真正的难点不在分发，在采集端跑在哪。抓取必须从能连上东财的网络发起 —— 而我们已经实测过，境外出口连不上 push2。这一条把「GitHub Actions 定时跑」 这个最省事的方案基本排除了（见第四节）。

二、账算清楚：集中采集省下多少

用户规模现在（各自直连东财）集中采集后说明
1 人13 次/天13 次/天没差别
10 人130 次/天，来自 10 个 IP13 次/天已经接近「200 个请求会被限流」的记录值
100 人1300 次/天，100 个 IP13 次/天每个用户都可能被单独限流，且体验随机
1000 人13000 次/天13 次/天集中采集的量与用户数完全无关

还有一个容易被忽略的收益：历史数据不再依赖用户自己开着程序。 现在的设计是「程序当天开过才存得到那天」——东财只提供当日分时，错过就永久没有。 集中采集之后，只要采集端在跑，所有用户都能拿到完整的历史，包括他装 sanhu 之前的那些天。

三、怎么分发

甲静态文件 + CDN 推荐
每个交易日生成一个 2026-08-14.json.gz，扔到对象存储 / GitHub Release / Pages。客户端按日期拉缺的那几天。
  • 零运维：没有进程要守，没有宕机概念
  • 成本近似为零：19 MB/年，任何 CDN 的免费额度都够
  • 天然可缓存：文件不可变，CDN 命中率接近 100%
  • 已有先例：SANHU_SEED_URL 就是这个模式
  • 缺点：只能按天取整包，做不了「只要某个板块」这种细粒度查询
乙真 API 服务器
跑一个后端，客户端按日期范围 / 板块查询。
  • 查询灵活，能做增量、能做筛选
  • 缺点：要运维、要花钱、会宕机，而且宕了所有用户一起没数据
  • 缺点：要处理限流、滥用、DDoS —— 这些都是新增的运维负担
  • 对 79 KB/天这个量级来说，灵活性买不到什么
Q1待你决策
用静态文件分发，还是跑一个 API 服务器？
数据量实测 79 KB/天、19 MB/年。这个量级下，服务器能提供的额外能力很有限，但运维成本是实打实的。

四、真正的难点：采集端跑在哪

红线境外机器抓不到东财 —— 这条排除了最省事的方案

2026-08-16 实测（详见前一份稿的红线 1）：挂境外节点时， push2 / push2his 全线 HTTP 000，而 fund.eastmoney.com 正常。 也就是说行情类接口对网络位置敏感。

GitHub Actions runner（ubuntu-latest，境外）
  → 抓 push2   极可能失败，且失败时你不在现场，只会看到一个空文件
  → 而分时数据错过当天就永久补不回来，静默失败的代价是永久性的

所以采集端必须跑在能稳定连上东财的网络里。你提到自己有服务器 —— 之前用它测 push2 返回过 200，那台是合适的落点。

采集端落点能否连东财可靠性说明
你的国内服务器✅ 已验证高 一个 cron + 一条命令。最直接的方案
GitHub Actions❌ 大概率不行低 免费、零运维，但 runner 在境外。失败还静默，数据永久缺失
你自己的电脑✅看你开不开机 就是现在的模式。周末/出差就断档
国内云函数 / 轻量服务器✅高 月租几块到几十块。如果不想用现有服务器，这是备选
必做采集失败要能被你知道

分时数据错过当天就永久补不回来，所以「静默失败」是这个功能最危险的失效模式 —— 等你三个月后打开回放发现缺了一堆日期，已经晚了。 采集脚本必须在失败时发出可见的信号（日志留存 + 失败时推送/邮件/企业微信任选其一）， 并且当天之内可以手动补跑（这个入口已经写好了，见 TestBackfillMinuteToday）。

Q2待你决策
每日采集跑在哪台机器上？
这题的约束是硬的：必须能连上东财的行情接口，且每个交易日 19:00 稳定执行。

五、整体链路

┌─ 采集端（国内，每交易日 19:00）────────────────────────────────────────┐
│  复用现有生产代码：sectorflow.Snapshot + SnapshotMinuteTop        │
│  ① 抓榜单（行业 + 概念）→ 落本地库                                     │
│  ② 抓 Top50 分时（串行 1.5 秒间隔，约 75 秒）→ 落本地库                │
│  ③ 导出当日数据包 2026-08-14.json.gz（实测 79 KB）                 │
│  ④ 上传到对象存储 / GitHub Release                                     │
│  ⑤ 更新 index.json（有哪些日期可用 + 各自校验和）                  │
│     └ 失败 → 告警（分时不可补，静默失败是最危险的失效模式）            │
└──────────────────────────┬─────────────────────────────────────────────┘
                           ▼  静态文件，CDN 可缓存
┌─ 分发（无服务器）──────────────────────────────────────────────────────┐
│  https://<cdn>/fundflow/index.json                                     │
│  https://<cdn>/fundflow/2026-08-14.json.gz   ← 不可变，永久缓存         │
└──────────────────────────┬─────────────────────────────────────────────┘
                           ▼
┌─ 客户端 sanhu（用户电脑）──────────────────────────────────────────────┐
│  新增 internal/sync：                                              │
│    · 启动时 + 每日一次拉 index.json，比对本地已有日期                  │
│    · 只下载缺的那几天（首次约 19 MB，之后每天 79 KB）                  │
│    · 写进同一套表 → 前端一行代码都不用改                          │
│  保留 直连东财的老路径作为降级（见 Q3）                            │
└────────────────────────────────────────────────────────────────────────┘

为什么客户端改动很小：数据最终写进的是同一套表 （sector_fund_flow_daily / _minute）， 所以榜单、热力图、回放这些上层功能完全不需要改 —— 它们只认表，不关心数据从哪来。

六、客户端还要不要保留直连东财

中心化之后有个新问题：当天的实时数据怎么办？ 采集端 19:00 才出包，但用户下午 2 点打开程序想看今天的盘中情况 —— 中心源里还没有。

三种处理方式，差别在于「是否允许客户端在特定情况下还去打东财」。

Q3待你决策
客户端还要不要保留直连东财的能力？
直连的代码已经写好且在跑，这题决定的是「留着、留一半、还是关掉」。

七、两件我必须提醒你的事

合规「自己用」和「分发给别人」是两回事

现在每个用户各自去抓东财的公开接口，性质接近个人使用。 改成你集中抓取、再分发给所有用户之后，性质变成了数据再分发 —— 这在法律和平台条款上是不同的一档，尤其当 sanhu 的用户规模变大、或将来涉及任何收费时。

我不是律师，没法给你结论。但这件事值得你在动手前自己确认一下， 至少心里有数：技术上没有障碍，风险在别处。 降低风险的常见做法：只分发衍生/聚合结果而非原始数据、标注来源、 提供关闭开关让用户可以选择自己直连、以及不对数据本身收费。

隐私别把 sanhu 的卖点弄丢了

README 里写着「工具不替你下单，不接入任何 AI 后端，不存储你的账户信息」， 而且是本地运行、首启无需联网。加了中心同步之后，务必守住：

· 同步是单向拉取，客户端不上传任何东西 —— 不要顺手加「统计用户数」之类的回传
· 请求里不带任何用户标识（无 token、无设备 ID、无 UA 指纹）
· 同步可以关闭，关掉后退回现在的直连模式，功能不残废
· 这几条最好写进 README，否则用户会合理地怀疑「它开始联网了，是不是也在传我的持仓」
