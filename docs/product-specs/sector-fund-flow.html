二、先说清楚：「资金流入」不是钱进出

这一节不是学术洁癖。做这个功能如果不把口径讲清楚，图表会直接误导决策 —— 而这个项目的定位是决策辅助工具，不是看图软件。

每一笔成交都有买方和卖方，钱没有净进出。「主力净流入 139 亿」不代表有 139 亿资金进了这个板块。 它的真实含义是：按单笔成交金额分档之后，大额成交里「主动买」比「主动卖」多出 139 亿的成交额。 主动买 / 主动卖靠成交价贴买一还是卖一来判定。所以它是一个推断出来的统计指标，不是资金流水。

东财的分档口径（其它数据商定义不同，这正是下面「不可比」的原因）： 超大单 ≥100 万元、大单 20–100 万元、中单 4–20 万元、小单 <4 万元；主力 = 超大单 + 大单。

E1五档净额的实测结构 真实数据
通信板块（BK1215）2026-08-14 收盘。两条实测校验写在图上 —— 它们正好印证了上面两句话。

实测校验一：主力 = 超大单 + 大单，精确成立。 122.23 + 16.84 = 139.07，与接口返回的主力净额差 0.0000 亿。说明分档是硬规则，不是估算。

实测校验二：四档相加 ≠ 0，而是 +0.35 亿。 如果这真是「资金进出」，全市场各档相加必须恒为零。实际留下 0.25% 的残差， 说明有一部分成交没有被归入任何一档（集合竞价、无法判定主动方向的中性盘）。 这是「它是统计推断而非流水账」最直接的证据。

还有一个跨源不可比的实证。同一只亨通光电（600487）、同一天： 东财给的主力净流入是 31.2 亿，新浪的 netamount 是 46.9 亿，差了 50%。 两家都没错 —— 分档阈值和主动方向判定规则不一样。

因此产品上必须守住两条： ① 只做同源比较，一个页面里绝不混用两家的数字； ② 文案不写「资金流入」四个字的字面义，UI 上要有一句话解释它是什么。 这条对应下面 Q1 的「术语提示」要求。

四、三条红线（必须在开工前认下来）

红线 1push2 会按 IP 封禁，量级远超注释里写的「数分钟」

实测证据（2026-08-16，同一台机器、同一条直连出口 218.82.106.180 上海电信）：

fund.eastmoney.com/pingzhongdata/000001.js   净值（项目在用）   HTTP 200  757 KB  ✓
fundf10.eastmoney.com/jbgk_000001.html       基金档案           HTTP 200   50 KB  ✓
push2.eastmoney.com/api/qt/clist/get         行情/资金流        HTTP 000          ✗
push2his.eastmoney.com/api/qt/...            历史行情           HTTP 000          ✗

同一时刻，从另一台机器（不同 IP）请求 push2 → 200

→ 同一个 IP 上，fund 通而 push2 不通；换个 IP，push2 就通。
   所以封禁作用在「IP × push2」这个组合上，与地域无关（该 IP 本就是国内电信）。

起因与时长：这个 IP 是在我做了一次 30 次/30 秒的突发压测之后开始不通的， 时间高度吻合，且 push2 限流在项目里早有独立记录： holdings_fetcher.go:109「刷 20 只基金就是 200 个请求，实测会被东财限流」、 global.go:20「push2 限流坑过一次」。 严格说单次事件证明不了因果，但这是目前最站得住的解释。 实测已持续 9 小时以上仍未解封 —— 老注释里的「持续数分钟」明显偏乐观，按小时计更稳妥。

排查陷阱（我在这上面栽过，写下来免得重蹈）：
判断「是不是我的 IP 被封了」时，不要用 api.ipify.org 这类境外服务去量出口 IP。 Clash 等工具默认是分流模式：国内域名走直连（真实宽带 IP），境外域名走代理（节点 IP）。 用境外服务量出来的是代理节点的 IP，和东财实际看到的完全是两回事 —— 我据此误判成「东财拒绝境外 IP」，绕了一圈。
正确做法：用国内的回显服务，路由才和东财一致 —— curl cip.cc。

对策（三轮反复后不变的部分）：照抄 holdings_fetcher.go 已验证的模式 「缓存优先 → 查库 → 都没有才联网，且放慢节奏」。全量板块排行一次只要 1 个请求， 盘中每 30 分钟一次 = 8 次/天；分时曲线按用户点击按需取，日均 <50 次。 另外两条已落进代码：① 失败指数退避 + 直接降级到缓存，绝不原地重试 （client.go 原本固定 1 秒重试 3 次，限流场景下等于火上浇油，已改）； ② 兜底判断不能只认「返回空」，「连接失败」也要走降级分支。 封禁按小时计这一点，让降级链条（内存 → 数据库）从「锦上添花」变成了必需品。

已解决找到了替代源：push2delay 是同一套 API 的延时版

2026-08-16 实测：push2 全挂时，push2delay.eastmoney.com 照常 200。 它是同一套 API 路径、同样的字段、同样的数值，只是行情延时 —— 对「盘中每 30 分钟看一次」 这个用法，延时几分钟看不出来。已实现为自动降级，主源失败就切备源，用户无感。

接口还活着、还返回 200，但值恒为 0 —— 沪深港通自 2024 年 8 月起已停止实时披露每日买卖净额， 现在只按季度公布持股。如果照着旧教程或旧代码抄，会得到一个「永远是 0」的图表而不自知，这是最危险的一种坏法。

对策：这一栏不做。如果非要给「外资视角」，只能退到季度持股变动，那是完全不同的产品形态，本期不纳入。

红线 3历史只有 120 天，想要更长必须自己攒

daykline 接口带 lmt=0（不限条数）返回的仍然只有 120 条， 时间窗恰好是 2026-02-13 → 2026-08-14，约半年。这意味着：

· 今天就能有：近半年的板块资金流趋势图，开箱即用。
· 今天不可能有：跨年度对比、「上一轮行情时这个板块的资金流长什么样」。
· 想要长历史，唯一的办法是从现在开始每天落库 —— 一年后才有一年的数据，没有捷径。

对策：这正是 Q4 要拍的板 —— 现在开始存，成本很低（约 25 MB/年）；不存的话一年后还是只有 120 天。

两个落地细节：① 收盘那次不能定在 15:05。实测 8-14 的数据时间戳是 15:39:31，收盘 40 分钟后东财还在更新，定早了会把未结算完的中间值写进库，所以固定 19:00。② 盘中 cron 要带交易日判断，不能只写 */30 9-15 * * 1-5 —— 节假日空跑虽然无害，但会白白往限流额度上撞。起始时间定 09:45（开盘前 15 分钟数据噪音大，且集合竞价未计入）。

七、抓哪些板块

三类板块字段完全一致，抓取成本也一样（各 1 个请求）。差别在信息质量：

行业板块（496 个） — 申万式分类，一只股票只属于一个行业。互斥、可加总、口径干净。 但实测发现层级混在一起：「通信」「通信设备」「通信线缆及配套」同时出现在榜上， 父子板块的资金会重复计算 —— 榜单前四名其实是同一件事。需要做层级去重，否则榜单会被一个热点刷屏（E2 那张图就是活例子）。

概念板块（504 个） — 「5G 概念」「人工智能」这类。一只股票可属于多个概念，严重重叠、不可加总， 但对普通用户更有解释力（「今天钱在往 AI 跑」比「往通信设备跑」好懂）。噪音也更大，蹭热点的概念板块很多。

地域板块（31 个） — 「江苏板块」这种，对基金决策基本没用。建议直接不做。

Q3已定
抓行业板块、概念板块，还是都要？
→ 行业 + 概念，首屏 Tab 切换。
抓取成本只多 1 个请求；落库量翻倍到 1000 行/交易日（约 25 MB/年，仍然很小）。必须配套做层级去重：实测 8-14 的榜单前四名是「通信 / 通信设备 / 通信线缆及配套 / 通信网络设备及器件」，父子板块资金重复计算，等于一个热点把榜刷屏了（第三节 E2 那张图就是活例子）。去重规则：同一父级下只保留净额最大的一个子板块，父板块单独成行并标注「含 N 个子板块」。

八、要不要落库（架构变更，Gate 要求明确确认）

架构变更现有 market 包是「不落库」的，这次要破例

internal/market/board.go 开头的设计注释写得很清楚： 「不落库：行情是易失数据，没有历史图表需求，缓存放进程内存」。 资金流功能正好有历史图表需求（E4 那张 120 天的图），所以要么破这个例，要么放弃历史视图。 按全局规范，架构变更必须在文档里点明并被你确认 —— 这就是本节存在的原因。

存储量实测估算：

· 日线：496 行业 + 504 概念 = 1000 行/交易日 × 约 250 日 ≈ 25 万行/年， 每行约 100 字节（代码/名称/五档净额/五档占比/收盘/涨跌）→ 约 25 MB/年。SQLite 完全扛得住。
· 分时：1000 板块 × 240 点 × 250 日 ≈ 6000 万行/年 → 约 2.4 GB/年。 不能全存，而且没必要 —— 东财当日现取只要 60ms。

所以分时的真正取舍是：东财只提供当日分时，收盘后就查不到昨天的分钟曲线了。 想要「回看上周三那天资金什么时候进的」，就必须每天收盘后把当天的分时存下来。 折中方案是只存当日榜单 Top20 板块的分时 → 20 × 240 × 250 ≈ 120 万行/年 ≈ 50 MB/年。

Q4已定
历史数据存到什么程度？
→ 存日线（全量）+ 每日榜单 Top20 板块的分时。约 75 MB/年。
这条确认了架构变更：新增 sector_fund_flow_daily 与 sector_fund_flow_minute 两张表，走 migrations/005_*.sql，正式打破 internal/market/board.go 开头写的「不落库」原则。该注释需要同步更新，说明「资金流是例外，因为它有历史图表需求」，否则下一个读代码的人会以为这是违规实现。另外建议加一条清理策略（保留 3 年），避免多年后数据库无声膨胀。

图表怎么画 —— 关系到二进制体积

更正：项目其实已经有图表库了。我最初写这份稿时说「没有任何图表库」， 是看漏了 —— static/index.html 第 9 行从 jsDelivr 载入了 ECharts 5， static/js/app.js 的 initChart() 一直在用它（还带了 ResizeObserver 处理容器变宽）。 下面 Q5 的结论已按正确前提重判。

embed.go 把整个 static/ 打进单个可执行文件 —— 这是「双击即用」的实现方式。 但 ECharts 不在 static/ 里，走的是 CDN。

由此暴露一个既有问题：断网时 ECharts 载不进来， 全站图表都画不出来，与 README「首启无需联网」的承诺冲突。 要修就把 ECharts 下载进 static/（约 +1 MB），这是独立于本功能的一笔改动，等你定。

图表用手写 SVG 还是引库？

你的补充「金融行业那个库最好就用那个」
这题我之前给错了前提，结论作废重来。 我当时说「项目现在没有任何图表库」，据此建议引 TradingView Lightweight Charts。 实际情况是：static/index.html 第 9 行早就从 CDN 载入了 ECharts 5， static/js/app.js 的 initChart() 一直在用。是我看漏了 grep 结果。
